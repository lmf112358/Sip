## 1. 需求 1：活跃时段要能排除午休

### 1.1 现状（已实现的部分）

- 每个任务一个时段：`active_start` ~ `active_end`，支持跨零点（如 22:00–02:00）。
- 全局另有一套「免打扰」：`dnd_enabled / dnd_start / dnd_end`，**只支持一条时段**。
- 冻结模型：暂停期间 `next_due += 1s`，剩余时间不变；恢复后接着走。

### 1.2 冲突点（两个，必须承认）

**冲突 A：午休和"免打扰"是同一个东西，现有设计重复了。**
`9:00–18:00` 的活跃时段里挖掉 `12:00–13:30`，本质上就是一段"安静时段"。而我上一版又单独做了一个"免打扰"设置。两个入口、两套开关、两种叫法，用户会问"这俩有啥区别"。

**冲突 B：两者的语义其实不同，不能简单合并成一个开关。**

| | 午休（离开座位） | 免打扰（人在，但不想被打断） |
|---|---|---|
| 典型时间 | 12:00–13:30 | 21:00–08:00 或 写代码时 |
| 结束后 | **应该立刻提醒**（回来该喝水了） | 不必立刻提醒 |
| 是否计入漏做 | 不计 | 不计 |

结论：**共用一套"安静时段"机制（引擎只有一份冻结逻辑），但每条时段带一个"结束后是否立刻补提醒"的属性。**

### 1.3 建议方案

**把「免打扰」升级为「作息 · 安静时段」列表，午休就是其中一条。**

```
设置 → 作息
  ☑ 启用安静时段
  ┌──────────────────────────────────────────────┐
  │ 12:00 – 13:30   周一~周五   回来后立刻提醒 ▾ │
  │ 22:30 – 08:00   每天         回来后不提醒   ▾ │
  └──────────────────────────────────────────────┘
  + 添加时段（最多 3 条）
```

- **作用范围：全局，不放到任务级。** 理由：午休是人的作息，不是任务的属性。放任务级意味着水/眼操/提肛/摸鱼 4 个任务各填一遍，改一次要改 4 处——纯负担。
- **任务的"活跃时段"保持不变**（`9:00–18:00`），语义变为"活跃时段 ∩ 非安静时段"。
- **引擎实现**：`pause_reason()` 里现有的 `"dnd"` 分支改成遍历列表；命中时行为与现在完全一致（冻结 `next_due`，不写 skip 记录，不影响跳过率）。
- **"回来后立刻提醒"** 的实现复用现有 `soft_land_until`：安静时段结束的那一刻，若任务已到期，给 0 秒缓冲（立刻弹）或 60 秒缓冲（让你坐稳）。

### 1.4 数据与验收

- 存储：`settings` 表新增键 `quietHours: [{start, end, days:[1..7], remindOnReturn: bool}]`（JSON）。
- 验收：
  1. 12:00 时剩余 3 分钟的水任务，到 13:30 结束安静时段后**剩余仍是 3 分钟**（不是重新计 45 分钟，也不是立刻补 3 次）。
  2. 安静时段内不产生任何 `skip` 记录，跳过率不变。
  3. 跨零点的安静时段（22:30–08:00）正常工作。

## 2. 需求 2：立即提醒的 bug、语义变更、首页要有记录和计时

### 2.1 Bug 定位

代码链是通的（按钮 → `trigger_now` → `show_reminder_all` → 建窗/复用窗 → 发 `remind-task` 事件），所以不是"没接上"，是下面三种之一：

1. **窗口复用但事件没到**：`reminder_0` 窗口第一次建成后一直 `hide()`，再次 `show()` 前发的 `emit` 若在 webview 未就绪时被丢弃，界面就停在旧任务上 → 表现像"点了没反应"。
2. **浏览器预览里压根没实现**：`mock.ts` 没接管 `trigger_now`，在 `localhost:1420` 里点当然没反应。
3. **任务行点击无响应**：任务页只有行尾的 ▶ 图标能触发，点行本身是死的——这跟你第 4 条需求是同一个体感问题。

**但这三条都不用修了**，因为语义一改，这个入口就不该存在（见 2.2）。真正要保住的是"预览提醒"，它会挪进设置的提醒分区，并且必须用真实 Tauri 环境验证一次（§5.4）。

### 2.2 语义变更带来的硬矛盾（这是要你现在决定的）

首页主卡片现在是这样的：

```
[ 128px 圆环：12:34 后提醒 ]   3/8 次 · 已喝 750/2000ml
[         完成一次（74px 大按钮）        ]   ← 已经是"提前完成"
   跳过    稍后 10 分钟    立即提醒
```

你说"立即提醒 = 用户提前完成了这项任务，重置计时，形成记录"——**这正是大按钮已经在做的事**。改完就有两个按钮干同一件事，而且小字那个更不显眼，用户会困惑为什么两个按钮效果一样。

**三个处理方式，我建议 A：**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 删掉"立即提醒"，三个小链接变为：跳过 / 稍后 10 分钟 / **改数量**（喝水选 150/250/350ml，其他类型隐藏） | 消除重复，且"喝多少"是真实缺口 |
| B | 保留"立即提醒"但改成"现在补一条记录"（弹出小面板选量/次数） | 与大按钮重复，只是多了个二次确认 |
| C | 保留"立即提醒"作为"预览这一次的提醒长什么样" | 预览属于设置的活，首页不该有 |

### 2.3 "首页应该有记录和计时"——这条我完全同意，而且现在确实缺

现状主卡有**计时**（圆环倒计时 + `12:34 后提醒`）和**今日进度**（3/8 次），但**没有"记录"**：用户看不到今天到底几点做了什么。

建议改成三层：

```
┌─ 主卡 ────────────────────────────────────────────┐
│  12:34 后提醒          今日 3 次 · 750/2000 ml      │  ← 计时 + 记录（总量）
│  [ 圆环倒计时 ]  [ 完成一次（大按钮） ]              │
│  跳过 · 稍后 10 分钟 · 改数量                        │
├─ 今日记录 ────────────────────────────────────────┤
│  14:02  喝水 250ml        ✓   (点一下可改/删)        │  ← 新增：流水
│  13:15  眼保健操          ✓                        │
│  12:40  喝水 250ml        跳过                      │
│  ...  展开全部                                      │
└───────────────────────────────────────────────────┘
```

- 每个任务卡/行补上「今日 N 次 · 下次 12:34」——**记录和计时两个数并排**，一眼看完。
- 后端需要新命令 `today_records(limit)`：从 `records` 表取当日明细（时间、类型、动作、数量）。
- 顺带解决一个隐患：**忘记点完成**。记录可删可补，比"漏了就漏了"体验好。

## 3. 需求 3：会议模式常驻

### 3.1 现状 vs 你要的

现状是**下拉菜单**（15/30/45/60/不限/到明天），选完才开启。你要的是**常驻开关**：点一下亮，再点一下灭。

这次改得对——会议场景 90% 是"临时被抓进去、不知道多久"，让用户先想"开多久"本身就是负担。

### 3.2 与现有 PRD 的直接冲突

PRD v1.2 里我写了"防忘记关闭：不限时长满 2 小时弹一次气泡"。

**常驻的语义就是"别烦我"，2 小时弹一个系统通知，本质还是烦你。** 这两条不能同时成立。

**建议：取消 2 小时弹窗，换成三个不打断的提示：**

1. 托盘图标加红点/变色（Windows 上 `set_title` 已可用，加个 `●` 前缀）。
2. 首页横幅常显：`● 会议模式已持续 2h 12m · 结束`（只有你回到主窗时看到）。
3. 主窗标题栏不显示倒计时（常驻没有倒计时）。

这样"防遗忘"依然存在，但只在**你主动看它的时候**出现。

### 3.3 交互（三态保留，形态改变）

```
[ 会议模式 ] 未开：描边按钮
[ ● 会议中 · 已 42 分钟 ] 已开：实心，点击即结束，右侧小字"15/30/60 分钟"可选
```

- 三入口不变：首页按钮、托盘菜单、`Ctrl/Cmd+Shift+M`。
- 15/30/60 分钟不再进首页，只在托盘子菜单里（给"我知道这个会开 30 分钟"的少数场景）。
- 重启后仍视为结束（防永久静音），首页会提示"上次会议模式已随重启结束"——这条已经在实现了。

## 4. 需求 4：任务界面点击即进入详情

### 4.1 现状问题

任务行现在是 `名称 | 间隔 | 目标 | ↑ ↓ ▶ ✎ ✕`，**点行没反应**，只有 5 个小图标能点。图标 22px、间距 4px，误点率高——这也是你"点了没反应"的另一半来源。

### 4.2 方案

- **整行可点** → 进入任务详情页（整页切换，右侧可返回）。
- 列表页只保留：`↑↓` 排序（或拖拽）、启用 Switch、hover 时才出现的 `⋯` 菜单（复制/删除）。
- 详情页内容：名称 / 图标 / 类型 / 间隔 / 单次值 / 目标 / 每日上限 / 活跃时段 / 生效星期 / 提醒方式（**默认"跟随全局"**）/ 今日记录 / 最近 7 天迷你柱图 / 底部"删除任务"。
- 首页的任务卡也一样：点卡片 → 详情页。
- 注意：Switch 和 `⋯` 要 `stopPropagation`，否则点开关就跳页了。

## 5. 需求 5：提醒个性化独立成区

### 5.1 必须先解决的设计冲突

现在提醒配置分散在两处：**任务**里有 `remind_style` + `template_id`，**设置**里有一张全局 `fullscreenImage`。

如果设置页再细化一套，用户改完设置发现没生效（因为任务里覆盖了）——这是这类 App 最高频的差评来源。

**规则（建议）：**

> 设置里的「提醒」= **按任务类型的默认值**；
> 单个任务里选「跟随默认」，或显式覆盖（全屏 / 消息窗 / 系统通知）。
> 任务编辑器里的提醒方式默认显示为「跟随默认（全屏）」，让人一眼知道现在用的是什么。

### 5.2 分区结构（4 块 + 1 个预览）

```
设置 → 提醒
  ① 形态与节奏
     默认形态：全屏 / 消息窗 / 系统通知（按类型分别设）
     全屏持续：12 秒（可关自动关闭，改成"必须交互"）
     消息窗停留：8 秒
     延后档位：5 / 10 / 15 分钟
  ② 外观
     全屏背景：8 套渐变预设 / 自定义图片 / GIF / 指定文件夹轮播
     遮罩浓度、背景模糊、是否显示倒计时、文案模板（9 套 + 自定义）
     消息窗皮肤：微信 / 邮件 / 系统 / 极简（四种已实现）
     消息窗位置：右下 / 右上 / 左上 / 左下
     微信皮肤可填：发送人昵称、头像文字、消息正文
  ③ 声音
     音效：内置 3 选（当前是合成音，加 2 个可选）/ 关闭
     音量、渐入时长、会议/专注中静音
  ④ 预览
     每个形态一个「预览」按钮：全屏预览 5 秒自动退出，消息窗预览 3 秒
```

### 5.3 别把"简单明了"做丢了

配置项一多，就违反你最初的要求。**默认只展开 ①②③④ 四行摘要，详细参数折叠在"更多"里。** 首次进入只看到"默认全屏 · 12 秒 · 8 套背景 · 预览"。

### 5.4 技术落点

- `Settings` 里 `fullscreenImage: String` 升级为 `reminder: { [type]: RemindProfile }`（JSON）。
- `RemindProfile`：`style / templateId / durationSec / toastSkin / toastPos / sound / volume / bgImage / dim / blur`。
- 任务级字段保留，空值 = 跟随默认。
- 新增命令 `preview_reminder(style, type?)`：直接开预览窗（复用提示窗），**必须在真实 Tauri 环境验证**（就是 §2.1 里那个没定位的 bug 的正解位置）。

## 6. 我另外建议补的 6 条（按价值排序，做不做你定）

1. **空闲检测（离开自动冻结）**：Windows 下 `GetLastInputInfo` 10 分钟无输入 → 冻结，回来 60 秒后提醒。午休时段是"计划内离开"，这个是"计划外离开"，两者互补，实现成本很低（已有锁屏检测的现成结构）。
2. **记录可补可删**：忘了点完成 → 主窗补一条；点错了 → 删掉。数据可信度直接上一个台阶。
3. **会议期间"临时放行"**：开会也要喝水的人不少，给一个"会议中仍提醒喝水"的开关（你第 3 条里我更倾向于做成一个默认关闭的选项）。
4. **提醒必须交互才算完成 vs 自动关闭**：全屏提醒如果自动关了，用户其实没喝水。建议统计里区分"确认完成"和"超时未响应"。
5. **预设任务库**：自定义任务现在要填 10 个字段，给 5 个预设（站立 / 深呼吸 / 远眺 / 伸展 / 记录心情）一键添加。
6. **周/月回顾卡**：CSV 导出有了，但没有"这个月比上个月多喝了 12 杯"这种一句话结论。

## 9. 定稿说明（按你的 4 个决定回写）

### 9.1 关于 ③：预览提醒放在首页 —— 我接受，但要约束三件事

你选了"保留为预览提醒"而不是我建议的删掉。**这个选择本身没问题**（用户确实需要确认"我设的提醒到底长什么样"），但必须绑定约束，否则会变成新的坑：

1. **必须真的能打开**。这正是"立即提醒点了没反应"的地方，所以预览功能的验收标准要写死：点击 → 3 秒内出窗 → 5 秒后自动消失 → 今日记录数不变、计时不变。实现时用真实 Tauri 环境验证（不能用浏览器 mock 验收）。
2. **文案必须改成"预览提醒"**，不能还叫"立即提醒"。"立即"意味着"马上给我来一次真的"，语义上是触发生效，用户分不清它和"完成一次"的区别。
3. **预览不能写记录、不能重置计时、不能消掉当前的 pending**。它是纯渲染预览，走 `preview_reminder(style, taskType)`，不复用 `log_action`。
4. 补充：会议模式中允许预览（这是用户主动行为，不属于"提醒"）。但预览窗关闭后不能把会议状态带乱。

### 9.2 关于 ④：会议一律屏蔽 —— 我保留一句提醒

"一律屏蔽"意味着会议中即使水喝完了也不会提醒。**这是你的明确选择，按此实现**，但建议在会议横幅上留一行小字（`会议中 · 所有提醒已暂停`），让人知道这是自己开的，不是软件坏了。这一行不影响屏蔽行为，只是降低"以为坏了"的误判。

### 9.3 其余两条按建议执行

- ① 全局最多 3 条安静时段：设置 → 作息，列表式编辑。
- ② 60 秒缓冲：复用已有 `soft_land_until`，不引入新机制。
